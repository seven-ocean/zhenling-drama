## BUG00025 修复：视频生成接口参数不匹配

### 根因
后端 `VideoController.generate()` 用 `@RequestParam String dramaId` 接收参数（期望 query string），但前端 `mediaApi.generateVideo()` 用 ofetch 的 `params` 发送。ofetch 的 `params` 行为不稳定——有时被正确编码到 query string，有时丢失，导致报错：
```
Required request parameter 'dramaId' for method parameter type String is not present
```

### 修复方案
**核心思路：POST 请求统一使用 JSON Body（@RequestBody），不再用 @RequestParam**

| 文件 | 改动 |
|------|------|
| **新建 `dto/VideoGenerateRequest.java`** | 视频生成请求 DTO，含 dramaId/episodeNumber/storyboardId/mode/prompt/imageUrl 等 |
| **VideoController.java** | generate() 从 11个 @RequestParam 改为 @Valid @RequestBody VideoGenerateRequest + 参数校验 |
| **media.ts** | generateVideo: `{ params }` → `{ body: params }`（JSON Body） |

### 数据流验证 ✅
MediaStudio/Workbench → `mediaApi.generateVideo({ dramaId, ... })` → POST JSON Body `/api/v1/videos/generate` → VideoController(@RequestBody) → VideoService.generate()

日志中的 FFmpeg 报错是环境问题（系统未安装 ffmpeg），非代码 bug。合成功能需要用户手动安装 FFmpeg 并加入 PATH。

## BUG00025 第四轮修复：videoUrl 存的是 file_id 而非 URL

### 根因（核心问题！）
用户实测发现视频记录的 `videoUrl` 字段存的是 **file_id**（纯数字如 `"389685784670407"`），不是真正的下载链接。完整数据链路：
1. MiniMax 视频任务完成 → 查询接口返回 `{"status": "Success", "file_id": "389685784670407"}`
2. `MiniMaxAdapter.pollVideoStatus()` 直接把 `file_id` 当作 URL 返回 `"completed:389685784670407"`
3. `VideoService.archiveVideoToStorage("389685784670407")` 把这个纯数字当 http URL 去下载 → 必然失败
4. **缺失步骤**：需要调 `GET /v1/files/retrieve?file_id=xxx` 解析出真实 `download_url`

### 修复（MiniMaxAdapter.java，2处改动）

| 改动 | 说明 |
|------|------|
| **新增 `fetchFileDownloadUrl(String fileId)`** | 调用 `GET /v1/files/retrieve?file_id={fileId}`，从响应 `{ "file": { "download_url": "https://..." } }` 提取真实下载URL |
| **改造 `pollVideoStatus()`** | SUCCESS 分支：先取 `file_id` → 调 `fetchFileDownloadUrl()` 解析为真实 download_url → 返回 `"completed:真实URL"`；兜底保留 video_url 和 raw fileId |

### 数据流修复后 ✅
```
MiniMax Video 任务完成 → pollVideoStatus() 取到 file_id
  → fetchFileDownloadUrl(file_id) → GET /files/retrieve → 真实download_url(https://...)
  → archiveVideoToStorage(downloadUrl) → RestTemplate下载视频字节 → uploadBytes() → OSS永久URL
```

## BUG00026 第三轮深度修复 (2026-04-20 23:31) — MiniMax API 规范完全对齐

### 背景

### 审计发现的5个严重偏差

| # | 偏差项 | 官方规范 | 当前实现(修复前) | 严重性 |
|---|--------|---------|----------------|--------|
| **1** | `resolution`参数 | ✅ 必填 `"1080P"` | ❌ **完全没有传** | 🔴 API报错或默认低分辨率 |
| **2** | 图生视频图片参数名 | `"first_frame_image"` (URL字符串) | ❌ 用了不存在的 `"reference_image_url"` | 🔴 图生视频API报错 |
| **3** | 主体参考参数结构 | `"subject_reference": [{type:"character",image:["url"]}]` | ❌ 用了错误的 `"subject_reference_image":"url"` | 🔴 主体参考API报错 |
| **4** | 模型按模式选择 | Hailuo-2.3 / Hailuo-02 / S2V-01 | ❌ 全部用Hailuo-2.3 | 🟡 首尾帧/主体参考效果差 |
| **5** | 旧版generateVideo() | 同上所有规则 | ❌ 硬编码+错误参数名 | 🟡 基础版不可用 |

### 修复方案（MiniMaxAdapter.java 核心重写）

#### 改动1: generateVideoMultiMode() 全面重写
- 新增 `resolveVideoModel(mode, userModel)` 方法：按模式自动选最优模型
  - TEXT_TO_VIDEO/IMAGE_TO_VIDEO → MiniMax-Hailuo-2.3
  - FIRST_LAST_FRAME → MiniMax-Hailuo-02
  - SUBJECT_REFERENCE → S2V-01
- 新增必填参数 `requestBody.put("resolution", "1080P")`
- 图生视频: `reference_image_url` → `first_frame_image`
- 主体参考: 字符串 → `Arrays.asList({type:"character", image:[url]})`
- 空prompt默认值增加 `[镜头缓慢推进]` 运镜指令
